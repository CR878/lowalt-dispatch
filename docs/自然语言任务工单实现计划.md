## 0. 目标

用户在控制台说一句自然语言，例如：

> 下周我想从上海虹桥机场送东西到浦东机场，你能给我规划路线吗？

Agent 收集证据（未来时段天气预报、限制区、地点解析、时间），生成一张**任务工单**和一条**推荐路线预览**，并在 Web 的任务中心 / 地图上能看到。

**验收口径**：能看到「任务 + 证据 + 路线」三样东西，且每一样都标明来源与仿真属性。不是可飞航线，不产生飞控指令。

## 2. 红线（写材料、做汇报前逐条核对）

1. **下周天气是「预报」，不是「当时的实测」**。Open-Meteo `hourly`/`daily` 最多 16 天，返回的是模式预报值，必须带 `kind:"forecast"`、来源、有效期和不确定性说明。
2. **禁飞区 / 限飞区目前只有仿真草稿**。没有真实空域数据源，工单里必须写「仿真草稿，非实测空域」，不得写成「已查询民航禁飞区」。
3. **虹桥 → 浦东的真实航线现在规划不了**。规划器不接收 WGS84；推荐路线只能是 `geometry_only` 的几何预览，明确标「仿真 / ENU 显示投影」。
4. **风速不进入能耗/绕路计算**（现版本未建模），气象数据只进「证据卡」，不得宣称「据此优化路线」。
5. **mock / 示例参数不得出现在效果描述里**；`dispatch_enabled` 保持 `False`。
6. **拿不到数据就返回 `unavailable`，绝不填占位数字**。
7. 不改 `core/models.py` 的 `Task` 契约、不接飞控、不产生执行回执；工单是独立的新对象。
8. 代码改了同步改本文与《事实文档.md》——项目铁律。

## 4. 网络可达性（实测，决定架构）

| 目标 | 本机沙箱 | 结论 |
|---|---|---|
| `api.deepseek.com` | 直连 HTTP 200 | 后端可直接调 |
| `api.open-meteo.com` | 早期 curl 超时 / httpx SSL 握手超时；但 2026-11-16 00:0x 由 `httpx.Client(trust_env=True)` **实际取到了** 16 天逐时预报；随后 curl 又因 schannel 吊销检查失败 | **间歇可达，不可依赖** |
| `nominatim.openstreetmap.org` | 代理 `CONNECT tunnel failed 502` | **后端在本沙箱基本取不到** |

设计后果：

- 后端证据工具必须做成**可插拔 + 显式降级**：请求失败返回 `{"status":"unavailable", ...}`，证据卡显示「未取到」，不含任何数字；取到时如实写 `kind:"forecast"`、来源与 `valid_for`。
- 「天气是否可以」不是固定答案，取决于当次网络，因此**必须先向用户确认地图定位与时间**，再去取；取不到就如实说取不到。
- 真实预报数据由 **P2 的浏览器侧** `weather.ts` 直接取（浏览器走用户网络，不经沙箱代理），再作为工具入参/上下文交给 Agent；现有前端天气功能就是这个模式。
- CI 环境（GitHub Actions）有外网，后端直连可用；测试一律 monkeypatch，不依赖真实网络。

## 9. 需求修正：先问全，再建单（2026-11-16 00:0x）

姜苏豪指出上一版方向错了：**不该"证据缺失也建一张残缺工单"**，而应像人一样先接住需求、再逐项问全，缺什么问什么，并附上地图定位让用户确认。已按此改。

**行为契约**：

1. 第一句先答「可以，完全可以做到」，并如实说明天气前提（需要地图定位 + 日期在 16 天预报窗口内）。
2. 逐项追问：**具体日期与起飞时刻**、**起终点名称是否正确并附地图定位请确认**、**载荷重量**、**优先级**。规则解析出的模糊时间只能作为"我暂按 X 理解，请确认"，不能当结论。
3. 信息未齐 → `create_task_intake` 返回 `needs_clarification`（`questions` / `map_pins` / `weather_feasibility` / `summary`），**不落库**。地图定位点为空时明确写「请在地图上点选」，不猜坐标。
4. 用户补齐后，工具从用户原话里只抽明确给出的值（日期时刻、起终点坐标、载荷、优先级），一次调用建单。

**三处稳定性修复（都有实测依据）**：

- 模型不会把用户补充的话映射成 JSON schema → 加 `evidence.extract_confirmations(text)` 规则兜底，只抽明确写出的值，`extract_confirmations("下周送东西，可以吗") == {}`。
- 模型反复调工具撞「推理步骤上限」→ `Toolset.terminal` 作为链路终止信号，`create_task_intake` 一有结论就结束本轮，由 `Engine.run` 用结构化结果渲染文本，不再依赖模型收尾。
- 追问文本由工具 `summary` 统一生成并被 `Engine.run` 覆盖，避免模型复述时漏项。

**两轮实测（`deepseek-flash`）**：

|---|---|---|
| 1「下周我想从上海虹桥机场送东西到浦东机场…」 | `resolve_real_place ×2 → get_airspace_zones → list_places → create_task_intake` | 5 项追问 + 地图定位提示，`STORED 0` |
| 2 补全「11月18日 09:00 / 起点 121.33,31.19 / 终点 121.80,31.14 / 载荷 2kg / P1」 | `resolve_real_place ×2 → get_airspace_zones → create_task_intake` | `STORED 1`，字段全部对上，天气 `ok`（真实预报值） |

一个有价值的细节：规则的「下周」推算成 2026-11-23，用户实际要的是 11-18 —— 正是追问让这个偏差被纠正，而不是被写进工单当成事实。
