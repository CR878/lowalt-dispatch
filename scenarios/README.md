# 场景包（M1）—— 待学生 B 设计

`eval/scenarios/v0.yaml` 里已经引用了 `R01~R04`（限制区）和 `L1~L4`（备降点），
但**几何还没画**。下面是需要补齐的文件和每条的设计约束。

> 为什么我不先画好：这些多边形放在哪儿是**实验设计**，不是填字游戏。位置决定了
> S4 到底能不能真的判不可行、S2 改线到底有没有第二条路。画的人必须能解释
> "为什么这里放限制区"，否则评委会问，而你们答不上来。

## 需要的文件

```
scenarios/
  v0/
    zones.geojson            # R01 R02 R03 R04 —— 限制区（含高度带与生效时间）
    landing_sites.geojson    # L1 L2 L3 L4 —— 备降点
    obstacles.geojson        # 建筑轮廓，用于净空与碰撞判定
    origin_destination.geojson  # 起降点标注（与 v0.yaml 的坐标对齐）
    README.md                # 每个区域的设计意图，一句话一个
  vehicles/
    placeholder.yaml         # 机型参数（A 负责）
```

## 格式要求

- GeoJSON `FeatureCollection`，坐标用**局部 ENU 米制**（x 向东，y 向北，范围 0—3000），
  与 `v0.yaml` 保持一致。等坐标原点确定后再整体转 WGS84。
- `properties` 必须包含：

| 字段 | 用于 | 例 |
|---|---|---|
| `id` | 与 yaml 里的 `zone_id` / `site_id` 对应 | `R01` |
| `is_simulated` | 一律 `true` | `true` |
| `source` | 来源说明 | `"自建虚拟城区 v0"` |
| `alt_min_m` / `alt_max_m` | 限制区高度带（备降点可不填） | `0` / `120` |
| `radius_m` | 仅备降点 | `25` |
| `compatible_vehicle_types` | 仅备降点 | `["placeholder"]` |
| `available_from` / `available_until` | 时窗，留空表示不限 | `null` |

## 设计约束（不满足这些，场景就白造了）

1. **R01~R04 必须压在主要航路上。** 如果限制区都在边角，S2 改线就退化成"什么都不用改"。
2. **S2 必须有第二条可行路线。** 每个 S2 场景改线后，新路线要能从另一侧绕过去，否则
   只能在 S2 里演示"任务不可行"，那不是 S2 想验证的东西。
3. **S4-03 要求所有备降点都失效** —— yaml 里已经把 L1~L4 全标了 `closed`，
   几何上要保证这四个点确实覆盖了航路两侧，否则"全都关闭"没有说服力。
4. **S4-05 要求初始能量低于保留量** —— 需要 `reserve_policy_wh` 先有值（A 提供）。
5. **备降点不能全在起点附近。** 否则任何一点都能就近降落，备降约束形同虚设，
   创新点直接被证伪。至少有一个点要在航路中后段。
6. **通信退化区要和限制区分开。** S3-03 的看点是"断连期间限制区消息到不了"，
   如果两个区重叠，就分不清是断连导致的还是本来就绕不开。
